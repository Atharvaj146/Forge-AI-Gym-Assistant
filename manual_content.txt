[12] [Heading 1] 1. Scope Decision ΓÇö What We Are Building Now
[13] [Normal] The original manual only sketched Home / Workout / Nutrition / AI CAM / Progress. The Product Explainer defines three phases. To avoid scope creep with a 2-person team, this manual locks scope to MVP (Phase 1) for the website, with Phase 2 items explicitly stubbed (UI present, feature disabled) where the rough manual already implies them (AI CAM).
[14] [Normal] Note: the rough manual explicitly asks for an AI CAM page pre-login with ΓÇ£basic instructions + small demo (before login)ΓÇ¥ and a ΓÇ£try AI CAMΓÇ¥ CTA that redirects to login. That page shell is in scope now; the actual MediaPipe pose-tracking engine is Phase 2 work per the explainer. Confirm this trade-off with whoever owns the roadmap before starting (see Section 14).
[15] [Heading 1] 2. Recommended Tech Stack
[16] [Normal] The explainer states architecture is an engineering decision, not a mandated stack. Given a 2-person team building inside Google Antigravity (agent-first IDE, browser-in-the-loop verification), the stack below optimizes for: fast agent-driven scaffolding, one shared language across frontend/backend, and low ops overhead.
[17] [Normal] Antigravity works across editor, terminal, and browser and verifies its own work with screenshots/artifacts ΓÇö so prefer stacks with clear visual output (React) and a runnable local dev server (Vite + Express) that the agent can browser-test after each task.
[18] [Heading 1] 3. Global Rules That Apply To Every Page
[19] [List Paragraph] Two states per page: Pre-Login (marketing/teaser, always ends in a CTA to Login/Signup) and Post-Login (functional, personalized). Build both from day one ΓÇö don't bolt post-login on later.
[20] [List Paragraph] Mobile-first responsive: design at 375px width first, then scale up to tablet (768px) and desktop (1280px+). Explainer states MVP is web-only, mobile-first.
[21] [List Paragraph] Global navbar: Home ΓÇö Workout ΓÇö Nutrition ΓÇö AI CAM ΓÇö Progress (post-login only) ΓÇö Login/Signup (pre-login) or Profile avatar + Logout (post-login).
[22] [List Paragraph] Global footer: About, Contact, Pricing, Terms, Privacy, Social links.
[23] [List Paragraph] Global AI Chatbot: a floating action button (bottom-right) on every post-login page, opening a chat panel. Not available pre-login except as a teaser tooltip.
[24] [List Paragraph] Every feature that requires personalization (personalised workout, personalised recipes, AI CAM, progress) is gated behind auth. Clicking it while logged out redirects to /login with a "continue to X after signup" return path preserved.
[25] [List Paragraph] Subscription gating: some post-login features are further gated by tier (Basic/Intermediate/Hardcore) ΓÇö see Section 10.

[120] [Heading 1] 9. AI Components ΓÇö What Actually Needs ΓÇ£AIΓÇ¥ in v1
[121] [Heading 2] 9.1 AI Workout Generator
[122] [List Paragraph] Input to the LLM/rules engine: goal, experience level, location, equipment, and (after week 1) recent WorkoutLog completion rate.
[123] [List Paragraph] Output: a structured JSON weekly plan (day ΓåÆ session_type ΓåÆ list of exercises with sets/reps) that maps directly onto WorkoutPlan/WorkoutPlanDay/WorkoutPlanExercise.
[124] [List Paragraph] Regeneration and single-exercise swap both call the same generator with a narrower scope (one day, or one exercise + ΓÇ£exclude XΓÇ¥).
[125] [List Paragraph] Progression rule: on each regeneration, difficulty step-up is driven by completion rate stored in WorkoutLog, not by the LLM guessing ΓÇö keep this a deterministic rule server-side, with the LLM only picking exercises/sets/reps within that difficulty band.
[126] [Heading 2] 9.2 Diet/Nutrition Filtering
[127] [List Paragraph] Mostly deterministic (v1 does not need an LLM here): filter Recipe by diet_tags matching the user's dietary_preference, and by a calorie target computed from goal + BMI/weight.
[128] [List Paragraph] Substitute suggestion: a lookup table mapping restricted ingredients ΓåÆ approved alternatives per diet type, checked at meal-log time.
[129] [Heading 2] 9.3 AI Chatbot
[130] [List Paragraph] System prompt fixed server-side: scope strictly to fitness/nutrition/app-usage, always include the no-medical-advice disclaimer, and inject the user's Profile + current WorkoutPlan/Nutrition summary as context on every call.
[131] [List Paragraph] No memory beyond ChatMessage history for that user; no external tool use required in v1.
[132] [Heading 2] 9.4 AI CAM (Phase 2 ΓÇö do not build the engine in v1)
[133] [List Paragraph] When it is built: MediaPipe Pose runs client-side in the browser (or a companion mobile capture), extracting joint coordinates; a rules layer compares joint angles per exercise against threshold ranges (e.g., knee valgus angle for squats) to flag form breaks and count reps.
[134] [List Paragraph] v1 only needs the AiCamSession table and page shell so this can be dropped in later without a schema change.

[137] [Heading 1] 11. Non-Functional Requirements
[138] [List Paragraph] Security: hash passwords (bcrypt), httpOnly + secure cookies for tokens, rate-limit /auth endpoints, validate all onboarding/profile input server-side (never trust client-side validation alone).
[139] [List Paragraph] Privacy/consent: explicit camera-permission prompt with a clear explanation before AI CAM activates (even in stub form).
[140] [List Paragraph] Performance: plan generation and dashboard load should each resolve in under 2ΓÇô3 seconds; explainer's success metric is sign-up-to-first-plan under 5 minutes end-to-end, so onboarding + generation latency matters.
[141] [List Paragraph] Responsiveness: every page usable at 375px width without horizontal scroll; test in Antigravity's browser-in-the-loop verification at both mobile and desktop breakpoints.
[142] [List Paragraph] Accessibility: form inputs labelled, color contrast checked, charts have a text/tabular fallback.
[143] [List Paragraph] No medical claims anywhere in copy ΓÇö chatbot, AI CAM, and nutrition pages all carry the same disclaimer language.
